## 3. 선행 결정

기술 스택은 다음과 같이 확정했다.

- 앱 형태: 웹앱
- 프레임워크: Next.js App Router
- 언어: TypeScript
- 스타일: Tailwind CSS
- 패키지 관리자: npm
- 로컬 개발 서버: `http://localhost:3000`
- AI API: 서버 측 Upstage API 연동 예정
- 테스트: Vitest 단위 테스트 및 Next.js 빌드 검증

실제 실행 명령은 `AGENTS.md`와 `package.json`에 반영했으며 `npm run check`로 포맷 검사, 린트, 테스트, 빌드를 통합 실행한다.

## 4. 구현 단계

### 단계 1. 저장소 작업 규칙 수립

루트에 `AGENTS.md`를 만들고 Codex와 팀원이 동일한 절차로 작업하도록 기준을 정의한다.

포함할 내용:

- 프로젝트 목적과 MVP 범위
- 실제 디렉터리 구조 및 각 영역의 책임
- 언어·프레임워크별 코딩 규칙
- 의존성 설치, 개발 서버 실행, 포맷, 린트, 테스트, 빌드 명령
- 작업 전 Issue 확인, 작업 후 검증, 결과 기록 절차
- 기존 사용자 변경사항을 보존하는 원칙
- 브랜치 및 커밋 규칙
- PR 본문에 변경 내용과 검증 결과를 남기는 규칙
- 환경변수와 비밀정보 처리 규칙

완료 조건:

- 새 팀원이 `AGENTS.md`만 읽고 설치·실행·검증 절차를 수행할 수 있다.
- 문서에 적힌 모든 명령이 현재 저장소에서 실제로 성공하거나, 적용할 수 없는 이유가 명시되어 있다.

### 단계 2. GitHub 작업 기능 준비 및 문서화

Codex 환경에서 다음 GitHub 기능을 사용할 수 있는지 확인한다.

- 저장소, Issue, PR 조회 및 요약
- PR 리뷰 댓글 확인과 수정 반영
- GitHub Actions 실패 로그 확인과 원인 분석
- 브랜치 생성, 커밋, Push, 일반 PR 생성

이 저장소를 사용하는 개발 환경에는 현재 다음 GitHub 스킬이 제공된다.

- `github:github`: 저장소·Issue·PR 조회와 요약
- `github:gh-address-comments`: PR 리뷰 피드백 확인 및 반영
- `github:gh-fix-ci`: GitHub Actions 실패 분석 및 수정
- `github:yeet`: 변경사항 커밋, Push, PR 생성

실행 시 확인할 사항:

- GitHub 연결이 `sunnypark87/AI-Builder-Sprint-Loop`를 읽을 수 있는지 확인한다.
- 로컬 `origin`과 GitHub 대상 저장소가 일치하는지 확인한다.
- GitHub 쓰기 작업은 대상 저장소·브랜치·PR을 명확히 확인한 후 수행한다.
- 스킬 자체는 개인 Codex 환경 기능일 수 있으므로, 저장소에는 팀원이 재현할 수 있는 사용 절차와 필요한 설치 조건만 문서화한다.

완료 조건:

- Issue 조회를 실제로 수행하고 결과를 확인한다.
- 샘플 변경을 일반 PR로 올리는 전체 흐름을 검증한다.
- 리뷰 댓글 또는 CI 실패가 없으면 해당 단계는 재현 가능한 점검 절차를 문서화한다.

### 단계 3. 환경변수 및 비밀정보 관리

프로젝트가 사용하는 환경변수의 이름만 담은 `.env.example`을 추가한다. 실제 키, 토큰, 개인정보는 포함하지 않는다.

예상 작업:

- `.env.example`에 필수·선택 변수와 용도를 주석으로 설명한다.
- `.gitignore`에 `.env`, `.env.*` 등 로컬 비밀 파일을 추가하되 `.env.example`은 추적한다.
- `README.md` 또는 `AGENTS.md`에 `.env.example` 복사 및 설정 방법을 기록한다.
- 로그, 테스트 fixture, 스크린샷에 API 키나 사용자 데이터가 남지 않도록 규칙을 정한다.
- 키가 유출되었을 때 즉시 폐기·재발급한다는 대응 절차를 적는다.

완료 조건:

- `git status`에 실제 `.env` 파일이 나타나지 않는다.
- 예시 파일만으로 필요한 환경변수 목록을 알 수 있다.
- 저장소 전체 비밀정보 검사를 통과한다.

### 단계 4. 공통 검증 명령 구성

Next.js와 TypeScript에 맞는 Prettier, ESLint, Vitest, Next.js build를 최소 구성한다. 팀원과 Codex가 도구별 세부 명령을 외우지 않도록 `package.json`의 `check`를 단일 진입점으로 사용한다.

필수 명령:

- `format`: 코드 포맷 적용 또는 검사
- `lint`: 정적 분석
- `test`: 자동 테스트
- `build`: 배포 가능한 빌드 생성
- `check`: 위 검증을 안전한 순서로 한 번에 실행

구현 원칙:

- 현재 프로젝트에 필요한 최소 규칙만 활성화한다.
- 로컬과 CI에서 동일한 명령을 실행한다.
- API 키가 없어도 단위 테스트와 정적 검증은 가능하도록 외부 API를 mock 처리한다.
- 실패 메시지로 어떤 단계가 실패했는지 바로 알 수 있게 한다.

완료 조건:

- 깨끗한 체크아웃에서 의존성 설치 후 `check`가 성공한다. 현재 승인된 실행 환경에서 통과를 확인했다.
- 의도적으로 포맷, 린트, 테스트 오류를 만들었을 때 각 검증이 실패한다.
- 검증 명령과 요구 런타임 버전이 `AGENTS.md`에 정확히 기록된다.

### 단계 5. Issue 및 PR 템플릿 추가

`.github/ISSUE_TEMPLATE/`과 `.github/pull_request_template.md`를 추가한다. Issue 템플릿은 원격 저장소에 이미 있는 Markdown 템플릿을 그대로 동기화해 사용한다.

Issue 템플릿 필수 항목:

- 배경과 목적
- 구현 범위와 제외 범위
- TODO 또는 완료 조건
- 관련 화면·자료·의존성
- 우선순위

PR 템플릿 필수 항목:

- 관련 Issue
- 변경 내용
- 검증 명령과 결과
- UI 변경 시 스크린샷 또는 데모
- 환경변수·마이그레이션·배포 영향
- 남은 작업과 알려진 제한

완료 조건:

- 새 Issue와 PR 작성 화면에서 템플릿을 선택하거나 자동으로 볼 수 있다.
- PR 작성자가 실제로 수행한 검증 명령과 결과를 남길 수 있다.

### 단계 6. 샘플 Issue로 전체 흐름 검증

작고 독립적인 문서 또는 코드 변경을 샘플 Issue로 만든 뒤 다음 순서를 실제 수행한다.

1. Codex로 Issue 내용과 완료 조건을 읽는다.
2. 로컬 코드와 관련 문서를 조사한다.
3. 별도 브랜치를 만든다.
4. 변경사항을 구현한다.
5. 포맷, 린트, 테스트, 빌드 또는 `check`를 실행한다.
6. 변경사항을 커밋하고 Push한다.
7. 변경 내용과 검증 결과가 포함된 일반 PR을 만든다.
8. 가능하면 리뷰 댓글 반영 또는 의도적인 테스트 실패를 통해 리뷰·CI 대응 절차도 확인한다.

샘플 작업으로 `/api/health` 엔드포인트와 최소 단위 테스트를 추가했다. 다음 단계에서는 이 변경을 별도 샘플 Issue와 일반 PR로 연결해 원격 작업 흐름을 검증한다.

완료 조건:

- Issue, 브랜치, 커밋, PR이 서로 연결되어 있다.
- PR 본문에 실행한 검증과 결과가 기록되어 있다.
- 검증 중 발견한 문제를 `AGENTS.md` 또는 관련 문서에 반영한다.

## 5. 예상 산출물

기술 스택에 따라 세부 파일은 달라질 수 있지만 최소 산출물은 다음과 같다.

```text
.
├── AGENTS.md
├── README.md
├── .env.example
├── .gitignore
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── ✨-feature-request.md
│   │   ├── 🐛-bug-report.md
│   │   └── ♻️-code-refactoring.md
│   └── pull_request_template.md
├── <package/task runner configuration>
└── <tests or smoke-test files>
```

필요한 경우에만 최소 CI 워크플로를 추가한다.

```text
.github/workflows/ci.yml
```

CI는 이슈의 직접 필수 항목은 아니지만, CI 실패 분석 흐름과 PR 자동 검증을 실제 확인하려면 유용하다. 일정이 촉박하면 로컬 `check` 명령을 먼저 완성하고 CI 연결은 후속 작업으로 분리한다.
