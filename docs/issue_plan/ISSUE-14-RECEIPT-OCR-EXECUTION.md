# Issue 구현 계획

## 1. 이슈 개요

- 대상 이슈: [#14 Upstage OCR 기반 영수증 검증 및 기부 집행 내역 등록](https://github.com/sunnypark87/AI-Builder-Sprint-Loop/issues/14)
- 우선순위: P0
- 상태: Open
- 담당자: HSHwan
- 작성일: 2026-08-02

기부처 담당자가 비공개로 영수증을 업로드하면 기존 Upstage Document OCR 연동으로 거래 정보를 추출하고, 합계·식별자 형식·집행 기간·예산 잔액·중복 여부를 결정적 규칙으로 검사한다. OCR 결과와 규칙 판정은 원본 근거와 함께 담당자가 검토·수정하며, 차단 오류가 없고 경고에 대한 확인 사유가 기록된 경우에만 집행 내역, 계획 예산 항목 연결, 검증 이력과 담당자 감사 정보를 원자적으로 등록한다.

이번 작업의 검증은 발행기관 원장 조회나 법적 진위 보증이 아니다. 서비스가 확인 가능한 문서 내용과 내부 데이터의 일관성, 중복 및 위험 신호를 판정하며, 화면과 데이터 모델에서도 이를 `진위 보증`으로 표현하지 않는다.

## 3. 선행 결정

구현 전에 확정해야 하는 기술·범위·외부 의존성을 기록한다.

- MVP의 등록 단위는 `영수증 1건 = 집행 내역 1건`으로 고정한다. 여러 영수증 묶음 등록과 거래명세서·세금계산서 처리는 후속 범위로 둔다.
- 지원 입력은 PDF, JPEG, PNG로 제한하고 기본 한도는 기존 계획 문서의 10MB·PDF 30페이지보다 영수증 사용 사례에 맞게 보수적으로 정한다. 정확한 한도는 구현 시점의 Upstage 공식 제한과 Vercel 요청 제한을 확인해 서버 상수, Storage, UI에서 동일하게 사용한다.
- 상태는 `analyzing`, `review_required`, `verification_warning`, `registered`, `analysis_failed`로 제한한다. 규칙 결과는 상태와 별도로 `passed`, `warning`, `blocked`를 가지며, `blocked`가 하나라도 있으면 등록하지 않는다.
- 동일 SHA-256 원본은 조직 범위에서 차단한다. 원본이 달라도 승인번호가 있으면 사업자등록번호·거래일시·합계·승인번호, 승인번호가 없으면 사업자등록번호·거래일시·합계의 정규화 키로 후보를 탐지한다. 의미 중복은 오탐 가능성을 명시하고 기존 내역 확인 경로를 제공하되 이번 이슈에서는 중복 강제 등록을 허용하지 않는다.
- 잔여 예산은 등록된 집행 내역의 합계를 기준으로 계산한다. 등록 RPC가 선택한 `expenditure_plan_items` 행을 잠근 뒤 잔액을 다시 계산하고 집행 내역·검증 이력 저장을 한 트랜잭션으로 수행한다. 클라이언트에 표시된 잔액은 권한 판단이나 최종 검증에 사용하지 않는다.
- 거래일이 기부금 수령 이후인지 검사하려면 권위 있는 결제 확정 시각이 필요하다. `donations.paid_at`을 추가하고 기존 데모 데이터는 `created_at`으로 백필하되, 실제 결제 연동 데이터의 출처가 확정되지 않으면 해당 규칙은 경고로 표시하고 `검증 통과` 근거에 포함하지 않는다. 영수증의 시간대 없는 거래일시는 국내 영수증 서비스 범위에 맞춰 `Asia/Seoul(+09:00)`로 해석하고 전체 시각을 비교한다.
- 사업자등록번호 체크섬은 형식 유효성만 뜻한다. 실제 사업자 상태와 영수증 발행 사실 확인은 외부 원장 연동 없이는 불가능하며 별도 이슈로 남긴다.
- OCR 문서 텍스트는 신뢰할 수 없는 데이터로 취급한다. HTML로 렌더링하거나 명령으로 실행하지 않고 React 텍스트 출력과 길이 제한을 적용하며, API 키·원문·전체 OCR 응답·카드 및 전화번호를 로그에 남기지 않는다.
- 모든 OCR 값은 담당자 검토 대상이다. 경고가 있으면 확인 사유를 필수로 받고, 수정 후에는 서버에서 전체 규칙을 다시 실행한 결과만 등록에 사용한다.
- 비식별 합성 영수증을 최소 8건 준비하고 구현 전에 필수 필드 정확 일치율 90% 이상, 거래일·합계 정확 일치율 100%, 결정적 차단 규칙 fixture 판정 100%를 통과 기준으로 고정한다. 기준 미달 시 지원 양식을 축소하고 미검증 범위를 기록한다.
- 카드사·국세청·현금영수증·가맹점 원장 API, 이미지 포렌식과 공개용 개인정보 마스킹은 이번 범위에 포함하지 않는다.

## 4. 구현 단계

### 단계 1. 집행·증빙 도메인과 원자적 보안 모델 설계

#### 작업 내용

- `expenditure_executions`, `execution_receipts`, `receipt_ocr_runs`, `receipt_verification_results`의 관계와 상태 전이를 정의한다.
- 집행 내역을 조직, 기부, 등록 완료 계획과 단일 예산 항목에 연결하고 모든 참조의 조직 일치를 DB에서 검증한다.
- `donations.paid_at` 추가와 기존 데이터 백필 정책을 마이그레이션에 반영한다.
- 조직 범위 원본 fingerprint 및 정규화 거래 키의 중복 제약과 생성자별 idempotency key를 설계한다.
- `receipt-documents` 비공개 버킷, `organizationId/pending/userId/uploadId/source.ext` 및 등록 후 객체 경로, 짧은 서명 URL과 고아 파일 정리 정책을 정의한다.
- 조직 멤버만 행과 원본을 읽고 service role만 상태 전이·등록을 수행하도록 RLS, Storage 정책과 함수 권한을 구성한다.
- 계획 항목 행 잠금, 서버 재검증, 잔여 예산 확인, 집행·증빙·검증 이력 저장을 하나의 security-definer RPC로 구현한다.

#### 완료 조건

- [ ] 다른 조직 사용자는 집행 내역, 검증 이력과 원본 파일에 접근할 수 없다.
- [ ] 조직·기부·계획·예산 항목이 일치하지 않는 참조는 DB에서 거부된다.
- [ ] 동일 영수증과 동일 idempotency 요청은 한 번만 생성·등록된다.
- [ ] 동시 등록에서도 예산 초과와 이중 차감 없이 전체 데이터가 원자적으로 저장된다.

### 단계 2. 영수증 파일 검증과 Upstage OCR 경계 확장

#### 작업 내용

- 영수증 파일의 MIME·확장자·시그니처·빈 파일·크기·PDF 페이지를 서버에서 검증하고 SHA-256 fingerprint를 계산한다.
- 기존 `document-ocr`의 계획 타입 결합을 제거하거나 호환 래퍼를 추가해 #7 회귀 없이 영수증에서도 재사용한다.
- 서버 전용 `UPSTAGE_API_KEY`로 OCR을 호출하고 성공 응답의 API·모델 버전, 페이지 텍스트와 신뢰도를 런타임 검증한다.
- 400·401·403·413·429·5xx, 타임아웃, 네트워크 실패, 비정상 JSON과 필드 누락을 안전한 내부 오류로 변환한다.
- 서명 업로드 URL 발급, pending 원본 검증·이동, 실패 시 삭제와 재시도 가능한 상태 전이를 구현한다.
- 요청 멱등성과 분석 lease를 적용해 중복 클릭·재시도가 불필요한 OCR 과금을 만들지 않도록 한다.

#### 완료 조건

- [ ] 허용된 실제 파일만 비공개 Storage와 OCR 요청으로 전달된다.
- [ ] 정상·외부 오류·타임아웃·비정상 응답이 결정적인 상태와 안전한 메시지로 변환된다.
- [ ] API 키와 원문이 브라우저 번들, 응답 및 로그에 포함되지 않는다.
- [ ] 기존 집행 계획 OCR 테스트와 등록 흐름이 그대로 통과한다.

### 단계 3. 영수증 구조화 파서와 검증 규칙 구현

#### 작업 내용

- 지원 양식의 레이블과 패턴을 기준으로 거래일시, 상호명, 사업자등록번호, 품목, 수량, 공급가액, 부가세, 합계, 결제수단과 승인번호를 추출한다.
- 날짜·시각·금액·사업자등록번호·승인번호를 정규화하고 각 값의 원문 근거, 신뢰도와 수정 기준값을 보존한다.
- 필수값·길이·금액 범위·품목 합계·공급가액과 부가세·영수증 합계를 검증한다.
- 사업자등록번호 체크섬, 계획 기간, 기부 결제 시각, 예산 잔액, 원본 fingerprint와 의미 중복 규칙을 독립적인 순수 함수로 구현한다.
- 규칙마다 안정적인 코드, 버전, `passed/warning/blocked`, 사용자 메시지와 민감하지 않은 근거를 생성한다.
- 낮은 신뢰도, 누락, 모호한 날짜와 미지원 양식은 추측하지 않고 경고 또는 차단 결과로 남긴다.

#### 완료 조건

- [ ] 대표 지원 양식의 필수 필드가 원문 근거가 있는 정규화 값으로 변환된다.
- [ ] 합계·식별자·기간·예산·중복 규칙이 정상, 오류와 경계 fixture에서 기대한 심각도를 반환한다.
- [ ] 파서가 원문에 없는 값을 만들거나 OCR 텍스트를 실행·HTML 렌더링하지 않는다.
- [ ] 등록 차단과 담당자 확인 경고가 코드·UI·DB에서 일관되게 구분된다.

### 단계 4. 업로드·분석·목록 상태 흐름 구현

#### 작업 내용

- `/partner/executions/new`에서 권한 있는 기부 내역, 등록 완료 계획과 예산 항목, 현재 잔액을 선택하도록 구현한다.
- 직접 업로드 후 `/api/partner/executions`가 인증·조직 권한·원본을 재검증하고 분석 레코드 생성, OCR, 파싱과 1차 규칙 실행을 조정한다.
- 성공 시 `review_required` 또는 `verification_warning`, 실패 시 `analysis_failed`로 전환하고 재시도 경로를 제공한다.
- `/partner/executions`를 실제 목록, 상태 필터와 오류·빈 상태로 교체하고 제목·금액·계획 항목·거래일·담당자 책임 상태를 표시한다.

### 단계 5. 원본 대조·재검증·집행 내역 등록 구현

#### 작업 내용

- OCR 추출값과 계획 예산 항목을 수정할 수 있게 하되, 원본 fingerprint와 OCR 기준값은 변경하지 않는다.
- 경고가 있으면 확인 사유를 필수로 받고 법적 진위 보증이 아니라는 안내를 표시한다.
- 제출 시 서버 스키마 검증과 모든 규칙을 다시 실행하고 최신 잔액·중복 여부를 RPC 안에서 재확인한다.
- 등록 완료 후 읽기 전용 근거 화면과 실제 목록으로 이동하며 공개·알림·마스킹 동작은 연결하지 않는다.

### AI 정확성 및 안전성 검증

- AI 동작 변경 여부: 해당. Upstage OCR 결과를 영수증 초안으로 구조화한다.
- 정확성 검증 결과: 필드 파서·스키마·규칙의 결정적 테스트와 실 Upstage 8건 평가가 PASS했다. 필수 필드는 32/32(100.0%), 거래일·합계는 16/16으로 사전 기준을 충족했다.
- 안전성 검증 결과: 악성 HTML/지시문을 값으로만 취급, 런타임 스키마 검증, 429·5xx·타임아웃·비정상 JSON의 안전한 오류, API 키·상류 응답 상세 비노출, 조직 RLS/Storage 격리와 담당자 확인 없는 자동 등록 금지를 테스트했다. 페이지 또는 품목 OCR 신뢰도가 0.8 미만이면 `ocr_review` 경고와 담당자 확인 사유를 요구한다.
- AI가 발견하거나 예방한 품질 문제: 초기 검토 화면에서 blocker가 있으면 값을 수정해도 재검증 버튼을 누를 수 없던 문제를 수정했고, Storage 정책 함수의 `authenticated` 실행 권한 누락을 전체 pgTAP 회귀에서 발견해 최소 권한으로 보완했다. 동시 등록 테스트를 추가해 계획 항목 잠금이 예산 이중 사용을 막는 것도 확인했다. 또한 범용 `UPSTAGE_MODEL=solar-pro3`가 OCR 요청에 전달되어 HTTP 400을 만들던 문제를 발견해 `UPSTAGE_OCR_MODEL` 경계를 추가하고 공식 OCR 기본 모델을 사용하도록 수정했다. 리뷰에서 프로세스 중단 시 영구 `analyzing` 상태와 낮은 OCR 신뢰도 누락을 발견해 2분 lease 재획득·token 기반 늦은 쓰기 거부·만료 작업 재시도와 저신뢰 경고를 추가했다. 후속 리뷰에서 최종 수정값의 의미 키 미갱신, 날짜 단위 결제 선후 비교, DB보다 느슨한 텍스트 길이 검증을 발견해 등록 RPC 재계산·서울 시간대 전체 시각 비교·API 422 사전 검증으로 보완했다.
- 최종 판정: PASS — 모든 완료 조건과 필수 정확성·안전성·저장소 검증이 통과했고 차단 항목이 없다.

### 차단 항목과 미검증 범위

- 차단 항목 없음.
- 비차단 보안 부채: `npm audit`에서 현재 Next.js가 포함한 postcss/sharp high 경고 3건이 남아 있다. 안전한 상위 Next.js 릴리스에서 해소 여부를 별도 추적한다.
- 실제 결제 연동에서 `donations.paid_at`의 권위 있는 출처와 운영 데이터 백필 정책은 배포 전에 확정해야 한다. 현재 마이그레이션은 기존 `paid` 행을 `created_at`으로 백필하므로 규칙에서 경고 근거로 취급한다.
- 원본 보존 기간과 pending 객체 lifecycle 삭제 주기는 운영 정책 확인이 필요하다.
- 발행기관 원장과 연동하지 않으므로 실제 발행 사실과 법적 진위는 검증하지 않는다.
