# Issue 구현 계획

## 1. 이슈 개요

- 대상 이슈: [#7 Upstage Document OCR 기반 기부 집행 계획 등록](https://github.com/sunnypark87/AI-Builder-Sprint-Loop/issues/7)
- 상태: Open
- 담당자: HSHwan
- 작성일: 2026-07-31

기부처 담당자가 PDF 또는 이미지 형식의 집행 계획서를 업로드하면 Upstage Document OCR API로 원문을 인식하고, 계획명·집행 기간·예산 항목·총액을 검토 가능한 구조화 데이터로 변환한다. OCR 결과는 자동 확정하지 않으며 담당자가 원본과 대조하고 수정한 값만 기부처 및 대상 기부 내역에 연결해 저장한다.

이번 작업은 업로드, OCR 분석, 검토·수정, 내부 등록까지를 완료 대상으로 삼는다. 기부자 공개, 알림, 집행 증빙, 완료 보고서는 포함하지 않는다.

## 3. 선행 결정

- 선행 이슈 [#6 Vercel-Supabase 연동 및 Auth 환경 구성](https://github.com/sunnypark87/AI-Builder-Sprint-Loop/issues/6)이 완료되고 서버에서 검증된 사용자와 세션을 조회할 수 있어야 한다.
- 조직, 조직 구성원, 대상 기부 내역의 테이블과 관계가 #7 구현 전에 존재해야 한다. #6은 도메인 스키마와 세부 RLS를 제외하므로, 해당 모델이 다른 이슈에 없다면 별도 선행 이슈를 만든다.
- MVP 지원 입력은 PDF, JPEG, PNG로 제한한다. 정확한 파일 크기·페이지 수·픽셀 제한은 구현 시작 시 Upstage 공식 문서와 Vercel 요청 제한을 함께 확인해 하나의 서버 상수와 UI 안내에서 재사용한다.
- 기본 처리 방식은 제한된 크기의 문서를 동기식 Route Handler에서 OCR하고 `AbortController` 타임아웃과 수동 재시도를 제공하는 것으로 한다. Vercel 실행 시간 내 완료가 보장되지 않으면 비동기 작업 큐 또는 Upstage 비동기 API를 별도 설계하고 범위를 재산정한다.
- 임의 형식 문서를 순수 OCR만으로 안정적으로 구조화할 수 없으므로 MVP에서 지원할 집행 계획서의 필드명과 표 구조를 먼저 고정한다. 알려진 레이블과 금액 패턴은 결정적 파서로 변환하고, 해석하지 못한 값은 추측하지 않고 빈 값 또는 `검토 필요`로 남긴다.
- 구조화 결과는 계획명, 시작일, 종료일, 예산 항목명, 설명, 금액, 총액으로 제한한다. 저장 전 모든 값에 길이·날짜·통화·음수 금지·합계 검증을 적용한다.
- 자동 추출 정확도 기준은 비식별 대표 문서 세트를 확정한 뒤 구현 전에 기록한다. 제안 기준은 필수 날짜·금액 필드의 정확 일치율 90% 이상이며, 최종 저장 값은 담당자 검토를 통해 100% 확인돼야 한다.
- 낮은 신뢰도 기준은 임의로 고정하지 않는다. 대표 문서 평가로 경고 임계값을 정하고, 신뢰도 제공 여부와 관계없이 모든 OCR 결과에 담당자 검토를 요구한다.
- 원본 파일과 OCR 원문·응답은 비공개 데이터로 분류한다. 서비스 로그에는 문서 본문을 기록하지 않고 요청 식별자, 상태 코드, 처리 시간, 내부 오류 코드만 남긴다.
- 원본 보존 기간, 삭제 정책, 동일 문서 재업로드 시 중복 처리 기준, OCR 비용 한도는 제품·운영 담당자와 확정해야 한다.
- Upstage Document OCR 공식 콘솔과 [UpstageAI Cookbook](https://github.com/UpstageAI/cookbook)을 구현 시점의 요청·응답 계약 기준으로 사용한다. Document Parse 또는 Information Extract 전환은 별도 이슈로 다룬다.

## 4. 구현 단계

### 단계 1. 도메인·상태·보안 모델 확정

#### 작업 내용

- #6의 Supabase 서버 클라이언트와 인증 사용자 조회 인터페이스를 확인한다.
- 조직 구성원과 대상 기부 내역의 기존 스키마·권한 경계를 확인하고 집행 계획의 참조 관계를 확정한다.
- `expenditure_plans`, `expenditure_plan_items`, `plan_ocr_runs` 테이블과 상태 전이를 설계한다.
- 상태를 `analyzing`, `review_required`, `registered`, `analysis_failed`로 제한하고 허용 전이를 서버에서 검증한다.
- 계획·항목 저장과 상태 전환을 하나의 DB 트랜잭션 또는 RPC로 처리한다.
- 비공개 원본 버킷, `organizationId/planId/source` 객체 경로, 조회용 서명 URL과 삭제 정책을 설계한다.
- 조직 구성원만 자신의 조직 계획과 파일에 접근하도록 테이블 RLS와 Storage 정책을 작성한다.

#### 완료 조건

- [x] #6의 인증 기반과 조직·기부 참조 모델이 준비됐거나 명시적인 선행 차단 항목으로 기록된다.
- [x] 계획, 항목, OCR 실행 이력과 상태 전이가 마이그레이션으로 재현 가능하다.
- [x] 다른 조직 사용자의 행과 원본 파일 접근을 RLS 및 Storage 정책이 차단한다.
- [x] 확인된 계획과 항목이 부분 저장 없이 원자적으로 등록된다.

### 단계 2. 파일 검증과 Upstage OCR 어댑터 구현

#### 작업 내용

- 허용 MIME, 확장자, 파일 시그니처, 빈 파일, 크기와 PDF 페이지 수를 서버에서 검증한다.
- 업로드 파일명을 데이터 경로나 로그에 직접 사용하지 않고 내부 UUID 기반 객체 키를 생성한다.
- `UPSTAGE_API_KEY`를 서버에서만 읽고 `multipart/form-data`로 Document OCR을 호출하는 어댑터를 구현한다.
- OCR API URL, 모델 기본값, 타임아웃을 한 모듈에서 관리하고 비밀 값은 오류 메시지에 포함하지 않는다.
- 성공 응답의 API·모델 버전, 페이지, 텍스트, 단어 위치와 신뢰도 필드를 런타임 검증한다.
- 400·401·413·429·5xx, 네트워크 오류, 타임아웃, 비정상 JSON과 필드 누락을 내부 오류 코드로 변환한다.
- 실제 네트워크 호출 없이 테스트할 수 있도록 `fetch` 또는 OCR 포트 인터페이스를 주입 가능하게 구성한다.

#### 완료 조건

- [x] 지원 파일만 OCR 요청으로 전달되고 클라이언트의 MIME 주장만 신뢰하지 않는다.
- [x] API 키가 브라우저 번들, 응답 본문, 로그와 테스트 fixture에 포함되지 않는다.
- [x] 정상·오류·타임아웃·비정상 응답이 결정적인 결과 또는 복구 가능한 실패 상태로 변환된다.
- [x] Upstage 호출은 자동화 테스트에서 전부 모킹된다.

### 단계 3. OCR 텍스트 구조화와 검증 구현

#### 작업 내용

- 합의한 계획서 레이블과 표 구조를 기준으로 페이지 텍스트를 정규화한다.
- 계획명, 기간, 예산 항목명·설명·금액, 총액을 추출하는 순수 함수를 구현한다.
- 쉼표, 원 기호, 공백, OCR 혼동 문자를 허용 범위 안에서 정규화하고 원문 근거와 수정 여부를 함께 보존한다.
- 날짜 역전, 음수·0원 정책, 빈 항목, 중복 항목, 항목 합계와 총액 불일치를 검증한다.
- 해석할 수 없는 값과 낮은 신뢰도 값은 임의 보정하지 않고 필드 단위 경고로 반환한다.
- OCR 문서 안의 명령문, HTML, 스크립트 문자열을 데이터로만 취급하고 실행·HTML 렌더링·추가 모델 지시로 사용하지 않는다.

#### 완료 조건

- [x] 대표 양식의 필수 필드가 정규화된 도메인 값으로 변환된다.
- [x] 누락, 모호한 값, 잘못된 날짜·금액과 합계 불일치가 저장 차단 오류로 표시된다.
- [x] 파서가 원문에 없는 값을 생성하거나 추측하지 않는다.
- [x] 경계·오인식·악성 문자열 fixture에 대한 단위 테스트가 통과한다.

### 단계 4. 업로드·분석 상태 흐름 구현

#### 작업 내용

- `/partner/plans/new`에 대상 기부 내역 선택과 파일 업로드 폼을 구현한다.
- 제출 시 인증과 조직 권한을 확인하고 `analyzing` 계획을 만든 뒤 원본 저장, OCR 호출, 구조화 결과 저장을 순서대로 처리한다.
- 동일 제출의 중복 처리를 막기 위한 idempotency key 또는 제출 잠금 방식을 적용한다.
- 성공 시 `review_required`로 전환하고 동적 검토 화면으로 이동한다.
- 실패 시 안전한 사용자 메시지와 내부 오류 코드를 저장하고 `analysis_failed` 상태에서 재시도할 수 있게 한다.
- 원본 저장 후 DB 처리 실패, OCR 성공 후 결과 저장 실패 등 단계별 보상 삭제 또는 정리 정책을 구현한다.
- `/partner/plans`를 실제 데이터와 상태 필터로 연결하고 등록 완료 상태를 공개 완료와 구분한다.

#### 완료 조건

- [x] 권한 있는 담당자의 정상 업로드가 `analyzing`에서 `review_required`로 전환된다.
- [x] 중복 클릭과 동일 재요청이 계획·파일·OCR 과금의 불필요한 중복을 만들지 않는다.
- [x] 각 실패 지점에서 부분 데이터와 고아 파일이 정책에 따라 정리되거나 재처리 가능 상태로 남는다.
- [x] 사용자가 실패 원인과 재시도 방법을 확인할 수 있다.

### 단계 5. 원본 대조·수정·내부 등록 구현

#### 작업 내용

- `/partner/plans/[planId]/review`에서 권한 검증 후 원본 서명 URL과 구조화 결과를 조회한다.
- 기존 `ReviewWorkspace`를 실제 PDF·이미지 원본과 편집 가능한 결과를 표시하도록 확장하거나 계획 전용 컴포넌트로 분리한다.

```bash
npm test -- --run src/lib/plans src/lib/upstage src/app/api/partner/plans

npm run check
```

실제 Upstage 정확성 평가는 자동화 테스트와 분리하고 승인된 환경에서 실행하며, API 키 없이도 정적 검증과 단위 테스트가 통과해야 한다.

- PDF·JPEG·PNG 시그니처, 10MB 크기, PDF 30페이지 제한과 SHA-256 중복 식별용 지문 검증을 구현함.
- Upstage Document OCR 서버 어댑터, 30초 타임아웃, 응답 런타임 검증과 안전한 오류 매핑을 구현함.
- 지원 레이블 기반 결정적 파서와 날짜·금액·필수값·합계·문자열 길이 검증을 구현함.
- Issue #6의 인증 기반에 최소 조직·구성원·기부 참조 모델과 계획·항목·OCR 이력, 조직 RLS, 비공개 Storage 정책, 원자 등록 RPC를 추가함.
- 등록 화면, 분석 상태 목록, 원본과 구조화 값을 함께 보는 검토·수정 화면, 업로드·조회·등록·같은 원본 재시도 API를 구현함.
- 외부 호출을 모킹한 단위·컴포넌트·API 테스트, 설정 없는 환경의 회귀 E2E, 로컬 Supabase 실통합 E2E와 pgTAP 검증을 추가함.
- 비식별 합성 문서 6종을 실제 Upstage에 호출하는 별도 정확도 평가를 추가하고 일반 품질 게이트에서는 제외함.
- Node 20 호환 Supabase 버전을 고정하고 Windows에서도 `npm run check`가 반복 가능하도록 Prettier 줄바꿈 설정을 보완함.
- PR 리뷰에 따라 인증 사용자의 계획·항목 직접 변경 권한을 제거하고, 상태 전이와 조직 권한을 검사하는 RPC로 쓰기 경계를 제한함.
- 업로드 응답 유실 시 같은 idempotency key를 재사용하고, 동시 생성 충돌 시 승자 계획을 반환해 중복 계획과 OCR 호출을 차단함.
- 후속 PR 리뷰에 따라 모든 계획 변경 RPC와 원본 업로드를 `SUPABASE_SECRET_KEY`를 사용하는 서버 전용 클라이언트로 제한하고 actor·조직 권한을 RPC에서 재검증함.
- 인증 사용자의 원본 Storage 업로드·삭제를 차단하고, 결제 완료(`paid`) 기부만 계획 생성과 최종 등록이 가능하도록 UI·서비스·DB에 동일한 규칙을 적용함.
- 분석 행에 2분 lease와 업로드 원본 경로를 기록해 중단된 분석을 단일 요청만 복구하고, 원본 없는 업로드 실패에는 재분석 대신 재업로드를 안내함.
- 분석 claim마다 lease token을 새로 발급하고 원본 기록·성공·실패 RPC에서 token 소유권을 검증해 만료된 worker의 상태 변경을 차단함.
- Vercel Function의 4.5MB 요청 제한을 우회하도록 signed upload URL을 발급하고 브라우저에서 비공개 Supabase Storage로 직접 업로드한 뒤, 서버는 작은 JSON 요청과 저장된 원본으로 검증·OCR을 수행하도록 변경함.
- 검증 전 pending 원본은 경로의 업로더 본인만 조회하고, 최종 계획 원본만 같은 조직 구성원에게 허용하도록 Storage SELECT 정책을 분리함.
- 동일 idempotency key 재사용 시 조직·기부·파일명·MIME·크기·페이지 수·SHA-256 fingerprint가 모두 일치해야만 기존 계획을 반환하거나 stale 분석을 재개하도록 강화함.
- 저장된 OCR 오류 코드를 기준으로 429·5xx·timeout·network 오류만 재시도하고, 400·401·403·413 오류에는 무효한 재시도 버튼을 노출하지 않도록 수정함.

### AI 정확성 및 안전성 검증

- AI 동작 변경 여부: Upstage Document OCR 호출과 OCR 텍스트의 계획 필드 변환을 추가했으므로 해당함.
- 정확성 검증 결과: 비식별 합성 대표 문서 6종을 실제 Upstage OCR에 호출해 필수 날짜·금액 30개가 모두 정확히 일치해 목표 90%를 넘는 100.0%를 기록함. 계획명도 6종 모두 기대값과 일치했고 제목 누락 문서는 값을 추측하지 않고 `title_required`로 남김.
- 안전성 검증 결과: API 키 누락·인증·용량·사용량 제한·5xx·타임아웃·네트워크·비정상 JSON·필드 누락을 모킹해 정제된 오류를 확인함. OCR의 HTML·스크립트 문자열은 React 텍스트와 데이터로만 처리되며 명령이나 HTML로 실행하지 않음.
- 실제 Upstage 키를 값 자체를 출력하지 않고 `.next/static`에서 검색해 브라우저 번들에 없음을 확인함. OCR 경로에는 원문 콘솔 로그와 `dangerouslySetInnerHTML` 사용이 없음.
- 조직 A/B 인증 컨텍스트의 행·원본 객체 격리, 수정 차단과 원자 롤백을 로컬 DB의 실제 RLS·RPC로 확인함.

### AI가 발견하거나 예방한 품질 문제

- 최신 Supabase 2.111.0의 Node 22 이상 요구가 저장소의 Node 20 지원과 충돌해 2.100.0 및 SSR 0.8.0으로 고정함.
- 클라이언트 MIME만 신뢰하지 않도록 파일 시그니처와 실제 PDF 페이지 파싱을 추가함.
- OCR 결과가 원문에 없는 필드를 추측하지 않도록 결정적 파서가 빈 값과 검토 오류를 반환하게 함.
- 긴 제목·항목·설명이 DB 제약에서 500으로 끝나는 문제를 발견해 애플리케이션과 RPC에 동일한 경계를 추가함.
- Windows 체크아웃의 줄바꿈 때문에 전체 포맷 검사가 실패하는 문제를 `endOfLine: auto`로 수정함.
- Postgres 17에서 `jsonb_to_recordset ... with ordinality` 조합이 실패하는 문제를 `jsonb_array_elements ... with ordinality`로 수정함.
- `auto_expose_new_tables=false`에서 명시적 테이블 권한이 없어 실제 API가 거부되는 문제를 인증 사용자와 서버 관리자 역할별 최소 권한으로 수정함.
- Supabase CLI `.temp` 생성물이 포맷·Lint와 Git 대상이 되는 문제를 세 도구의 제외 규칙에 반영함.
- Vercel Supabase 환경 별칭이 남아 설정 없음 테스트가 실제 네트워크로 진행되는 문제와 설정 검증보다 `cookies()`가 먼저 실패하는 문제를 수정함.
- 인증 사용자가 Supabase REST로 계획 상태와 등록 항목을 직접 변경해 검증·감사 정보를 우회할 수 있는 권한 문제를 제거함.
- 응답 유실 재제출과 같은 idempotency key의 동시 요청이 중복 계획·OCR 과금 또는 500 오류를 만들 수 있는 경쟁 조건을 제거함.
- 인증 사용자가 REST로 내부 `SECURITY DEFINER` RPC를 호출해 OCR 결과나 분석 상태를 위조할 수 있는 경계를 서버 전용 secret 클라이언트로 차단함.
- 조직 구성원이 등록 원본을 직접 삭제해 감사 근거를 소실할 수 있는 Storage DELETE 정책을 제거함.
- 서버 중단 후 `analyzing` 상태가 영구 정체되거나 원본 없는 실패에 동작하지 않는 재시도 버튼이 노출되는 문제를 lease와 복구 가능 상태 구분으로 수정함.
- 취소·환불된 기부 내역에 집행 계획을 생성하거나 등록할 수 있는 문제를 UI·서비스·RPC의 `paid` 검증으로 차단함.
- 10MB 원본을 Vercel Function 본문으로 전송해 4.5MB 초과 구간이 운영에서 413으로 실패하는 문제를 signed direct upload로 제거함.
- 동일 idempotency key에 다른 파일을 넣어 원본 객체와 감사용 fingerprint·MIME·파일명이 불일치할 수 있는 문제를 RPC 충돌 검사로 차단함.
- 인증 실패·잘못된 요청·상류 용량 초과처럼 재시도 불가능한 OCR 오류에도 재시도 버튼이 표시되는 문제를 오류 코드 기반 복구 상태로 수정함.
- 서버 RPC 직접 호출로 재시도 불가능한 오류를 재분석하거나, 재시도 가능한 실패에서 새 계획과 원본을 중복 생성할 수 있는 문제를 차단함.
- 검토 요청이 OCR 출처 필드를 위조하거나 설명·신규 항목 수정을 감사 이력에서 누락할 수 있는 문제를 저장된 OCR 초안 비교로 차단함.
- 원본 직접 업로드 후 분석 요청이 서버에 도달하지 않으면 pending 객체가 남는 문제를 사용자 범위 정리 API로 보완함.
- 분석 응답을 검증하기 전에 pending 경로를 해제해 HTML 오류나 서버 인계 전 실패에서 원본 정리를 건너뛰는 문제를 차단함.
- 동일 OCR 항목 ID를 반복 제출해 복제 항목을 미수정 상태로 등록할 수 있는 문제를 애플리케이션과 RPC의 유일성 검증으로 차단함.
- 재분석 성공 응답이 유실된 뒤 같은 계획을 다시 요청하면 409로 처리해 새 계획과 OCR 호출을 만들 수 있는 문제를 완료 상태 멱등 조회로 차단함.
- 등록 시 계획 수준 OCR 초안을 검토값으로 덮어써 제목·기간·총액의 원본 근거를 잃는 문제를 별도 `ocr_draft_data` 보존으로 차단함.
- 404·422 등 영구 Upstage 4xx를 재시도 가능한 `upstream_failure`로 저장하는 문제를 `upstream_rejected` 코드로 분리함.
- lease 만료 후 새 worker가 분석을 인계해도 이전 worker가 성공 또는 실패 상태를 기록할 수 있는 경쟁 조건을 세대별 lease token 검증으로 차단함.
- 조직 ID만 검사하는 Storage SELECT 정책 때문에 같은 조직의 다른 사용자가 검증 전 pending 원본을 읽을 수 있는 문제를 업로더 UUID 검증으로 차단함.

### 차단 항목과 미검증 범위

- 차단 항목 없음.
- 배포 환경에는 계획 변경 Route Handler 전용 `SUPABASE_SECRET_KEY` 설정이 필요하다. 브라우저 접근이 가능한 `NEXT_PUBLIC_*` 변수로 선언해서는 안 됨.
- 실제 Upstage 평가는 개인정보가 없는 합성 지원 양식 6종 기준이다. 운영 기부처의 다양한 실제 스캔 품질과 지원 범위 밖 임의 양식은 후속 데이터셋 평가가 필요함.
- `npm audit --omit=dev --audit-level=high`는 기준 브랜치와 동일한 Next.js 16.2.12의 `next`, `postcss`, `sharp` 경로에서 고위험 3건·치명적 0건을 보고함. 제공되는 자동 수정은 Next 9.3.3으로 역행하므로 적용하지 않았으며 Issue #7 신규 코드에 한정된 차단 항목으로 분류하지 않음.
